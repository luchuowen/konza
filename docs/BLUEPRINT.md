# BLUEPRINT — Konza Elevators Website Redesign

**Read this before docs/KONZA_SPEC.md and docs/KONZA_MEDIA_PROMPTS.md, in Session 0, and keep its rules in CLAUDE.md for every session after.** This document is the "why" behind the other two — the spec tells you what to build, this tells you what it has to feel like and never become.

## Who this is for and why it exists

Konza Elevators & Escalator Co. Ltd is a real, 13-year-old Nairobi elevator and escalator installer with 50 documented completed projects, an authorized Fuji Elevator distributorship, and three genuine client testimonials — and a website that currently undersells all of it: no Services or Projects page in its own navigation, no email address published anywhere, an un-renamed "Home Main" browser tab, and a broken "News item not found!" widget on its own homepage. NAVAC Global sold this client a KES 200,000 redesign built on a page-by-page audit and a competitive benchmark against two named local rivals (Greymark Elevators, Lift Escalator Kenya) who are currently ahead of Konza on the two things that decide whether a visitor becomes a lead: a working enquiry mechanism, and verifiable proof of work. This build closes that gap and then goes further, because deeper research turned up an asset the original proposal didn't even know about: 50 real named projects, not 4.

**The mission in one sentence: build something that makes Konza look like the most credible, most capable elevator company in Kenya, because on the facts, it already is one of them — the site just needs to stop hiding that.**

## The non-negotiables

1. **Nothing invented.** Every fact, client name, product spec, testimonial and number in this build traces to docs/KONZA_SPEC.md, which itself traces to Konza's own live site, company profile PDF, and manufacturer catalogs. If something isn't in the spec, it doesn't go on the site. Items marked `[CONFIRM]` stay visibly unresolved — a business decides its own hours and email address, not an AI agent.
2. **Zero AI slop.** No warm-cream-and-serif template feel, no "near-black plus one acid accent" AI-default palette, no oversized broadsheet-hairline headlines, no generic staged stock photography, no fabricated certifications. If a page reads like it was generated rather than designed, it has failed — regenerate it, don't ship it.
3. **Authentically Kenyan, not generically African.** Every image brief in docs/KONZA_MEDIA_PROMPTS.md is grounded in real Nairobi specifics — Upper Hill's actual density, the 2026 zoning liberalization to 75 storeys, equatorial hard light, jacaranda streets against glass towers. Not a Western skyline pastiche wearing an "Africa" filter.
4. **Every buyer segment gets what they actually look for first**, per the four audiences in docs/KONZA_SPEC.md §1: developers/contractors want compliance and delivery capability, facility managers want SLAs and response times, institutions/healthcare want verifiable references, homeowners want price clarity and an easy way to book a consultation. Don't design for one and forget the other three.
5. **WhatsApp is a first-class channel, not an afterthought.** 72% of Kenyan B2B buyers prefer WhatsApp for vendor onboarding and quotes over email or a web form. The in-page WhatsApp widget is as important as the Get a Quote form — build both, wire both to the same lead record.
6. **Mobile-first is not a checkbox.** Kenya's internet access is 134% mobile-connection penetration against 40% fixed-broadband-equivalent reach, and data cost is a real constraint for real visitors. Design at 390px first. Compress everything. A beautiful desktop site that's heavy or broken on a mid-range Android phone has failed this client's actual audience.
7. **No two NAVAC client sites share visual DNA.** This is Konza's system — the navy/red "Vertical City" documentary language in docs/KONZA_SPEC.md §4 — built for this brand's real red-and-navy mark. The accent isn't an invented brand red: `#E8453D` (with `#7A1014` as its deeper secondary) was sampled directly from the actual Konza logo after it was extracted from the live site, so the palette is literally the client's own mark, refreshed and rationed rather than reused as-is or discarded — exactly what the signed proposal promised.
8. **Quality bar: 9.8/10, not 9/10.** That tenth of a point is the pre-launch audit in Session 9 of docs/KONZA_BUILD_WORKBOOK.md — the difference between "looks done" and "verified done." Don't skip it, don't rush it, don't mark it complete without evidence.
9. **Design is approved, not proposed — build it exactly.** Unlike a typical build workbook, this one isn't asking Claude Code to interpret a brief. The home page and the Projects/Portfolio page exist as real, Playwright-verified static HTML mockups (`mockups/design-final-vertical-city.html`, `mockups/design-projects-page.html`) that the client has explicitly signed off on ("That design is perfect, i love it"). Every other page has content locked and layout creatively authorized within that same fixed system — see docs/KONZA_SPEC.md §6 for exactly how much latitude each page has. Nothing in docs/KONZA_BUILD_WORKBOOK.md should reopen a design decision that's already closed.

## What "premium" means for this specific brand

Not luxury-fashion minimalism, and not a heavy industrial-catalog look either. The reference point is: **KONE.com's documentary-photography confidence and scale-driven trust signals, RIO Property's editorial typography and considered motion, and CARBO's technique of making an invisible mechanism visible** — applied to a genuinely Kenyan, genuinely mid-sized, genuinely trustworthy vertical-transportation company that competes locally against Otis, KONE and Schindler and should look like it belongs in that conversation, while being unmistakably Nairobi's own rather than a translated multinational template. The full rationale for choosing this direction over the two alternatives considered is in docs/KONZA_SPEC.md §1 — read it, it explains what to protect if you're ever tempted to drift toward a more generic "clean SaaS" look partway through the build.

## Stack & deploy target

- **Frontend:** Next.js (App Router) + TypeScript + Tailwind CSS + a motion library, per docs/KONZA_BUILD_WORKBOOK.md Session 0/1.
- **Data:** Firestore (Native mode), same Google Cloud project as the hosting target. The build workbook stubs this behind a `LeadRepository` interface so real Firestore wiring is a later, separate step — do not attempt to provision a live Firestore project or touch DNS from inside the numbered build sessions; that comes as its own dedicated prompt once the client has reviewed the built site.
- **Hosting:** Firebase App Hosting (`firebase deploy --only apphosting`), Blaze plan required.
- **Domains — two, don't conflate them:** `konza.navac.co.ke` is the NAVAC-controlled staging/preview subdomain, used to give the client (and Owen) a working link to review before the engagement is fully signed off — it is not the final production URL. The eventual production domain is Konza's own `konzaelevators.co.ke` (their `.com` has lapsed and is out of scope per the signed proposal; re-registering it is a separately-scoped item). Do not point any code, canonical URLs, or `og:url` metadata at `konza.navac.co.ke` as if it were permanent — treat it as a preview, and use relative/environment-driven URLs so the eventual cutover to the client's own domain is a config change, not a rebuild.
- **Repo:** https://github.com/luchuowen/konza — this is where every session in docs/KONZA_BUILD_WORKBOOK.md commits and pushes.

## The three documents, and how they relate

- **docs/KONZA_SPEC.md** — the facts, the content, and (§4/§6) the approved design system and page-by-page layout direction. What to say and how to lay it out, on which page, backed by which source. Read this before writing a single line of copy.
- **docs/KONZA_MEDIA_PROMPTS.md** — the exact imagery, one self-contained Nano Banana Pro prompt per asset, with the exact filename every build session must match against, plus the note that the real logo itself is never generated. Generate these images BEFORE running the build sessions that need them (Sessions 2–7) — the workbook checks for each file by name and falls back to a styled placeholder gradient, never a broken image, if one isn't ready yet.
- **docs/KONZA_BUILD_WORKBOOK.md** — the 10 copy-paste Claude Code sessions (0–9) that turn the above into a shipped site. This version is deliberately **build-only**: it assumes all research and design decisions are already made, so Session 0 alone scaffolds the repo and writes a complete `CLAUDE.md` from scratch — you do not need to also hand Claude Code `Software_Factory_Playbook.md` for environment setup, though attaching it as background reading won't hurt anything. Each session is scoped to fit inside a ~250k-token context window so quality never degrades from context overload, each ending in a Playwright-verified evidence checklist, each committed and pushed before you `/clear` and move to the next.

## What happens after Session 9

The site is built, verified, and pushed — but not deployed, and not wired to real Firestore or a real domain yet. That's deliberate: Owen reviews the built site first, then requests a separate, focused Claude Code prompt (through the same conversation that produced these four documents) to provision the actual Firebase project, enable Firestore for real, and map `konza.navac.co.ke` as the working preview link — DNS records, SSL provisioning, and the roughly 24–48-hour propagation window all need to happen deliberately, with the client's DNS access if the eventual cutover target is their own domain. Don't attempt any of that inside the numbered build sessions above.
